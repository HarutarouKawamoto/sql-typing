## なぜ

- **`pressKey(state, target, key)` にした**：状態に target を持たせると1キーごとに大きな target をコピーし直すことになる。状態は小さな値だけにして、target は作り直さない
- **打ちながらの実行は「句の最後の文字」で起こす**：数字の途中（`LIMIT 1` と `LIMIT 10`）や `DESC` の前で実行すると、意味の違う表が一瞬出る。句の最後の文字なら、そこまでが1つの意味のまとまりになる
- **判定を `canRunWhileTyping` 1つにした**：最初は画面と検証で別々に「先頭が SELECT か」を正規表現で見ていたが、先頭のコメントで食い違うと実装検証で指摘された。`SELECT ... INTO`（表を作る）も途中で実行させない
- **打てない文字を検証で止める**：区切りでないところの Enter・Tab は画面で打てない。文字列の中に改行がある問題を1つ入れるだけでゲームが止まるので、エンジンで受けるより、問題を作るときに止める方が単純
- **キーの判定と実行の間引きを `typing-keys.js` に分けた**：React の部品を描くテストの道具（@testing-library/react）を足さずに、競合しやすいところだけを単体テストするため。作り直したときに予約が止まる不具合も、この形で構造的になくなった
- **苦手を回数で見せる**：機能設計書の割合（ミス ÷ 打った回数）は、1回に同じ記号を何度も間違えると100%を超える（キーワードの「打った回数」は1語につき1回で数えるため）
- **最高記録はランク → 正確さ → 速さの順に比べる**：機能設計書は「速さが速い方」だったが、速くて正確さの低い回（ランクC）が、正確な回（ランクA）を上書きしてしまう（実装検証の指摘）。最初は「ランク → 速さ → 正確さ」にしたが、本人の判断で同じランクの中でも正確さを先にした
- **localStorage は `getBrowserStorage`（データレイヤー）だけで触る**：画面から触らない決まり（ESLint）を守り、使えない環境では作り物を返して遊ぶことは続けられるようにした
- **入力エリアを真ん中に大きく、表はすぐ下に**：最初は機能設計書のとおり2列（左に打つところ、右に表）にしたが、本人が打ってみて「入力エリアが画面の真ん中に大きく出てほしい」と希望した。表を下にしたのは、打った瞬間の変化が視線を少し下げるだけで見え、列も横いっぱいに使えるため。全体の見た目は一覧画面の作業で決める
- **サイト全体を125%の大きさにした**：本人がブラウザで125%表示にしたときの大きさがちょうど良いと希望した。CSS の `zoom` ではなく、ルートの文字を125%にして、余白・幅も rem に直した（ブラウザの文字の大きさの設定がそのまま効き、`html { font-size }` 1か所で全体を変えられる）
- **`.claude/launch.json`**：画面を目で確かめるため。Claude Code のプレビューが前の一時フォルダを見に行ったので、そちらにも同じ設定を置いた（プロジェクトの外なので、この一覧には入らない）
