## なぜ

- **土台づくりは `main` で作った**：コミットが1つもない状態で `feature/` を切ると、最初のコミットがそのブランチに入り、`main` が空のまま残るため（本人と確認済み）。次の作業から `feature/<作業名>` にする
- **PGlite を使う検証は入れていない**：`SqlRunner` がまだないため。「正解SQLが動く・0行でない・間違いの選択肢が不正解になる・順番が1つに決まる」は次の作業「DBが動く」で `tests/integration/data-validation/` に足す（`problems.test.js` の冒頭のコメントにも書いた）
- **制約を3か所に分けた**：1ファイルの中で決まるもの → Zod、ファイルをまたぐもの → `cross-checks.js`（純粋な関数で単体テストできる）、PGlite が必要なもの → 統合テスト。どこに足せばよいか迷わないように機能設計書にも書いた
- **選択肢どうしと、表示用SQLの中を探すときで比べ方を分けた**：選択肢どうし（`normalizeForCompare`）は文字列の中も含めて大文字・小文字を無視し、紛らわしいものを厳しめに止める。表示用SQLの中を探すとき・display と answer を比べるとき（`normalizeSqlForMatch`）は、TypingEngine と同じく文字列の中だけ区別する（検証が `'Mug'` と `'MUG'` を同じと見なすと、実際には打てない問題が通ってしまうため）
- **`fetch` などを「警告」から「エラー」にした**：フラット設定では、レイヤーのブロックで `no-restricted-globals` を書くと共通の指定が置き換わる。レイヤーごとに「エラー」の禁止（localStorage など）と同じルールに並べる必要があり、1つのルールに警告とエラーを混ぜられないため。「使うときは理由をコメントに書く」は `eslint-disable-next-line` ＋ 理由で満たせる
- **`varsIgnorePattern` を `^(_|[A-Z][a-z])` にした**：JSX の中でだけ使うコンポーネント名（`App`）の誤検知を避けつつ、使っていない `UPPER_SNAKE_CASE` の定数は見つけるため（`eslint-plugin-react` を足すより依存が少ない）
- **schema の import の許可を正規表現にした**：`group: ['*', '!zod', '!./*']` の `!` による除外が `./` に効かず、同じフォルダの import まで止まったため。`./../` で抜けられないよう `\./(?!\.)` にした
- **会話の行数の上限を kind 別にした**：最初は全問12行にしていたが、設計書の「3〜8行（ターニングポイントは10行程度）」より緩く、通常の問題の長すぎる会話を止められなかったため
- **check-review-files.js をルートで実行し `-z` にした**：`git diff` はルート基準、`git ls-files` は今いるフォルダ基準でパスを出すため、サブフォルダから実行すると食い違った。日本語のパスは `-z` なしだと8進のエスケープで返り、必ず不一致になった（どちらも実装検証で一時リポジトリを使って見つかった）
- **`.strict()` のままにした**：Zod 4 では `z.strictObject` が推奨だが、動きは同じなので書き換えていない
