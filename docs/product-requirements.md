# プロダクト要求定義書 (Product Requirements Document)

> 元にした資料：[docs/ideas/initial-requirements.md](ideas/initial-requirements.md)（壁打ちの決定1〜18）。このPRDの中の「（決定N）」は、そのメモの番号を指す。

## プロダクト概要

### 名称
**SQL Typing**（仮）- 打って、動きを見て、覚えるSQL

### プロダクトコンセプト
- **打って覚える**：SQLを実際に打ち込むタイピングで、キーワードと記号の並びを手に覚えさせる。同じ問題を「なぞる → 選ぶ → ヒントありで書く → ヒントなしで書く」の4モードで、手助けを減らしながら繰り返す
- **動きが見える**：打ったSQLをブラウザの中の本物のPostgreSQLで実行し、句ごとに行が消える・まとまる・つながる様子をアニメーションで再生する。「書いた順」と「動く順」の違いを毎回目で確かめる
- **仕事の物語で覚える**：ネットショップに入った新人データ担当が、社内の依頼をSQLで片付けて活躍していく俺つええ系のストーリー。「このSQLは現実のどの場面で使うのか」が依頼文から伝わる

### プロダクトビジョン
SQLを「暗記した文法」ではなく、「手が覚えていて、頭の中でテーブルが動いて見えるもの」にする。

学習者は1つの依頼を4つのモードで繰り返し、打つたびに、DBの中で何が起きたかを目で見る。

初級の `SELECT` から、上級のインデックス・実行計画・トランザクションまでを、同じお店のDBの上で一続きの物語として学ぶ。

最後には、白紙から書いたSQLが「なぜその結果になるのか」「なぜ遅いのか」を自分の言葉で説明できる状態を目指す。

提供する価値：
- 打ち慣れ：SQL特有の記号（`(` `'` `,` `*`）とキーワードを、止まらずに打てるようになる
- イメージ：実行順（FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY）と、各句での行の変化を説明できるようになる
- 実務感：DBは最初から最後まで同じお店のもの。テーブルのつながり（ER図）が少しずつ頭に入る

### 目的
- 初級〜上級のSQLを、4モードで繰り返し練習できる環境を作る
- SQLの実行過程（句ごとの中間結果、上級ではインデックス・実行計画・ロック）を見える形にする
- サーバーなし・ログインなしで、ブラウザを開けばすぐに練習できるようにする
- 問題を YAML ファイル1つ追加するだけで増やせる仕組みにする

## ターゲットユーザー

### プライマリーペルソナ：本人（Web開発を学習中の開発者）
- Next.js・Astro でWebサイトを作った経験がある。DBは ORM（Drizzle など）越しに触ることが多く、SQLを直接書いた量は少ない（※仮定。違えば直す）
- 現在の課題：
  - SQLを書こうとすると、キーワードの順番や記号で手が止まる
  - `GROUP BY` や `JOIN` が DB の中で何をしているのかイメージできず、結果が想定と違ったときに原因がわからない
  - 「インデックスで速くなる」「トランザクションで守る」を言葉では知っていても、実感がない
- 期待する解決策：ゲーム感覚で毎日少しずつ打ち、動きを見ながら、白紙からSQLを書ける状態になる
- 典型的な使い方：PCで1日15〜30分。新しい問題をモード1・2で数問 → 前日の問題をモード3・4で復習 → 章の最後にターニングポイントに挑戦
- 端末：キーボードのあるPC（Chrome / Edge）

## 成功指標(KPI)

測定はすべて、ブラウザに保存される学習記録（localStorage）から行う。外部への送信はしない。

### プライマリーKPI
- **初級1章の修了**：MVP完成から4週間以内に、初級1章の全9問（8問＋ターニングポイント）をモード4でクリアする
- **打ち慣れ**：モード1の入力速度（1分あたりの正しい入力文字数）が、初回プレイの平均から +30% 以上（MVP完成から4週間以内）
- **正確さ**：モード1・2の正確さが、直近10問の平均で 95% 以上

### セカンダリーKPI
- **継続**：MVP完成後4週間のうち、学習記録のある日が週4日以上
- **見える化の利用**：クリアした問題のうち、ステップ再生（見える化A）を最後まで見た問題が 80% 以上
- **苦手の解消**：結果画面の「苦手な記号・キーワード」上位3つの打ち間違い率が、4週間で半分以下になる
- **章の追加**：中級の章（P1）を、MVP完成から8週間以内に遊べる状態にする

## 機能要件

### コア機能(MVP)

MVPは**初級1章（8問＋ターニングポイント1問）**。この時点で、4モード・判定・見える化・ストーリー・DBの地図・用語辞典の仕組みをすべてそろえる（決定16）。

#### 1. SQL実行環境（PGlite）

**ユーザーストーリー**:

学習者として、本物のDBの動きを体験するために、ブラウザの中でPostgreSQLを実行できる環境が欲しい

**受け入れ条件**:
- [ ] ページを開くと、ブラウザの中で PGlite が起動し、お店の初期データ（初級では `products` テーブル、20〜30行）が入った状態になる
- [ ] 書いたSQLの実行結果（表）またはエラーが返る
- [ ] 問題を始めるたびに、DBがその問題の初期状態に戻る。「リセット」ボタンでもいつでも戻せる
- [ ] 外部のサーバーにSQLやデータを送らない（ネットワーク通信は最初のファイル読み込みだけ）

**優先度**: P0(必須)

#### 2. 章と問題の一覧・進む条件

**ユーザーストーリー**:

学習者として、どこまで進んだかと次に何をやるかがわかるように、章と問題の一覧と、問題ごとのモード別クリア状況が欲しい

**受け入れ条件**:
- [ ] 章（初級・中級・上級）と、各章の問題が一覧で見える。各問題に、4つのモードのクリア状況（4つの星）が表示される
- [ ] 1問をどれかのモードでクリアすると、次の問題が開く（決定7）
- [ ] 章の最後のターニングポイントは、モード3か4でクリアしたときだけクリア扱いになり、次の章が開く
- [ ] クリア済みの問題は、いつでもどのモードでも遊び直せる
- [ ] まだ開いていない問題は、題名だけ見えて選べない

**優先度**: P0(必須)

#### 3. ストーリー（依頼の会話）

**ユーザーストーリー**:

学習者として、そのSQLがどんな場面で必要になるかを理解するために、問題ごとに社内の人からの依頼を会話で読みたい

**受け入れ条件**:
- [ ] 各問題の最初に、依頼する人（店長・先輩・営業など、固定の数人）との短い会話（3〜8行）が表示される
- [ ] クリア後に、驚く・感謝するなどの反応の会話（1〜4行）が表示される（俺つええ系、決定6）
- [ ] 会話はクリック／Enterで送れる。「スキップ」で飛ばせる
- [ ] ターニングポイントには、章の山場になる長めの会話（10行程度）がある
- [ ] 会話・説明文は日本語。SQLとデータの値は英語と数字だけ（決定13）

**優先度**: P0(必須)

#### 4. モード1：なぞり書き

**ユーザーストーリー**:

学習者として、SQLの形を手に覚えさせるために、表示された正解SQLをそのまま打ち写すタイピングがしたい

**受け入れ条件**:
- [ ] 正解SQLが薄く表示され、打った文字が濃くなっていく
- [ ] 打ち間違えるとその場で止まり、間違えた文字が赤く光る。正しいキーを押すまで先に進まない
- [ ] キーワードの大文字・小文字は区別しない（表示は大文字）。文字列 `'...'` の中は区別する
- [ ] 単語の区切りは Space 1回。表示上の改行は Space か Enter のどちらでもよい
- [ ] 1つの句を打ち終えるたびに、横の結果の表がその場で変わる（見える化C）
- [ ] 最後まで打つとクリア。結果画面を表示する（機能9）

**優先度**: P0(必須)

#### 5. モード2：打って選ぶ

**ユーザーストーリー**:

学習者として、似ている書き方の違いを考えながら打つために、空欄に入る選択肢を打つことで選ぶタイピングがしたい

**受け入れ条件**:
- [ ] SQLの一部（1〜3か所）が空欄になり、空欄に来るとその下に選択肢が2〜4つ並ぶ
- [ ] 選択肢は、似ているが意味が違うもの（例：`WHERE price > 1000` / `HAVING price > 1000` / `ORDER BY price`）にする
- [ ] 打ち始めた文字に合う選択肢が光る。どれか1つを最後まで打ち切るとその選択肢で確定する（決定4）
- [ ] 正しい選択肢で確定すると先に進む。間違った選択肢で確定すると不正解になり、なぜ違うかの一言説明が出る。その空欄はやり直せる
- [ ] 空欄以外の部分は、モード1と同じルールで打つ
- [ ] 1つの句を打ち終えるたびに、結果の表が変わる（見える化C）

**優先度**: P0(必須)

#### 6. モード3：ヒントありで書く／モード4：ヒントなしで書く

**ユーザーストーリー**:

学習者として、自分の力でSQLを書けるようになるために、依頼文だけを見て白紙からSQLを書きたい

**受け入れ条件**:
- [ ] SQLを自由に書ける入力欄がある（複数行可）。Ctrl+Enter で実行する
- [ ] モード3では、ヒントを段階的に開ける（例：①使う句 ②句の順番 ③SQLの骨組み）。開いたヒントの数は記録される
- [ ] モード4ではヒントは出ない
- [ ] 実行すると判定（機能7）が行われ、正解ならクリア、不正解なら理由が表示されて書き直せる
- [ ] 実行のたびに結果の表と見える化A・Bを見られる

**優先度**: P0(必須)

#### 7. 判定

**ユーザーストーリー**:

学習者として、正しい別解でも認めてもらいつつ、練習したい書き方からは外れないように、実行結果で判定してほしい

**受け入れ条件**:
- [ ] 書いたSQLと正解SQLを両方実行し、結果の表（列の数と値）が同じなら正解とする（決定12）
- [ ] 問題が順番を指定しているとき（`ORDER BY` が必要な問題）だけ、行の順番も比べる
- [ ] 問題ごとに「必ず使うキーワード」「使ってはいけないキーワード」を設定できる。結果が合っていても条件を満たさなければ「結果は正しい。ただし今回は◯◯で書いてみよう」と表示してクリアにしない
- [ ] SQLがエラーになったら、PostgreSQLのエラーメッセージと、その和訳・よくある原因を表示する（初級で出やすいエラー10種類以上の和訳を用意する）
- [ ] 不正解のときは、どこが違うか（行数が違う／列が違う／値が違う／順番が違う）を表示する
- [ ] 書き換え系（`INSERT`/`UPDATE`/`DELETE`、中級以降）は、実行後のテーブルの中身を比べる

**優先度**: P0(必須)

#### 8. 見える化

**ユーザーストーリー**:

学習者として、SQLがDBの中でどう処理されるかをイメージできるようになるために、句ごとに表が変わっていく様子を見たい

**受け入れ条件**:
- [ ] **A. ステップ再生**：実行後、SQLの各句に実行順の番号が付き、1句ずつ光りながら、その時点の表が表示される。再生・一時停止・1ステップ進む・戻るができる
  - [ ] `FROM`：テーブルの全行が並ぶ
  - [ ] `WHERE`：条件に合わない行が赤くなって消え、「30行 → 12行」のように行数の変化が出る
  - [ ] `SELECT`：使わない列が消える。`AS` で列の名前が変わる
  - [ ] `DISTINCT`：重なった行が1つにまとまる
  - [ ] `ORDER BY`：行が並び替わる動きが見える
  - [ ] `LIMIT`：指定した行数より後ろが消える
- [ ] **B. 実行順の並び替え**：実行の直前に1〜2秒、書いた順に並んだ句が実行順に入れ替わるアニメーションが流れる。設定で止められる
- [ ] **C. 打ちながら変化**：モード1・2で、句を打ち終えるたびに結果の表が変わる（機能4・5）
- [ ] 初級で扱うすべてのキーワード（決定8の初級の範囲）について、A の動きがある

**優先度**: P0(必須)

#### 9. スコアと苦手の記録

**ユーザーストーリー**:

学習者として、打ち慣れてきたことを実感するために、速さ・正確さと、よく間違える記号・キーワードを知りたい

**受け入れ条件**:
- [ ] モード1・2の結果画面に、1分あたりの正しい入力文字数・正確さ（%）・かかった時間を表示する
- [ ] 速さと正確さから、ランク（S/A/B/C）を付ける。基準の数値は機能設計で決める
- [ ] モード3・4の結果画面に、かかった時間・実行した回数・開いたヒントの数を表示する
- [ ] 打ち間違えた文字・キーワードを記録し、結果画面に「苦手な記号・キーワード」の上位3つを出す
- [ ] 問題ごと・モードごとの最高記録を保存し、一覧画面から見られる

**優先度**: P0(必須)

#### 10. DBの地図

**ユーザーストーリー**:

学習者として、お店のDBの全体像をつかむために、テーブルとそのつながりを図で見たい

**受け入れ条件**:
- [ ] その章で使えるテーブルを、箱（テーブル名と列名・型）と線（つながり）の図で表示する
- [ ] 今の問題のSQLが触っているテーブルが光る（中級以降は、使っている結合の線も光る。今は、線の両方のテーブルを触っていれば光る）
- [ ] 章が進むとテーブルが増え、新しく増えたテーブルには印が付く
- [ ] 箱をクリックすると、そのテーブルの中身（先頭20行）が見られる

**優先度**: P0(必須)

#### 11. 用語の英語と和訳・用語辞典

**ユーザーストーリー**:

学習者として、キーワードの意味を英語から理解するために、知りたいときだけ英単語の意味と和訳を見たい

**受け入れ条件**:
- [ ] 画面上のSQLのキーワードにカーソルを当てると（スマホではタップ）、英語の意味とSQLでの意味が出る（例：`WHERE` — 英語：どこで／〜であるところの　SQL：条件で行を絞り込む）
- [ ] 普段は表示しない（タイピング中に勝手に出てこない）
- [ ] 全キーワードを一覧で見られる「用語辞典」ページがある。各キーワードに、英語の意味・SQLでの意味・短い例・初めて出てくる問題へのリンクがある
- [ ] MVPでは、初級の範囲のキーワードすべてを収録する

**優先度**: P0(必須)

#### 12. 学習記録の保存

**ユーザーストーリー**:

学習者として、次に開いたときに続きからできるように、進み具合が自動で保存されてほしい

**受け入れ条件**:
- [ ] クリア状況・最高記録・苦手の記録を、ブラウザ（localStorage）に自動で保存する
- [ ] 保存データが壊れていて読めないときは、初期状態で起動し、そのことを画面に表示する（アプリが止まらない）
- [ ] 設定画面から学習記録をすべて消せる（確認を1回はさむ）
- [ ] 学習記録をファイルに書き出す・読み込む（別のPCに移すため）

**優先度**: P0(必須)。ただし書き出し・読み込みは P1

#### 13. 端末による表示の切り替え

**ユーザーストーリー**:

学習者として、スマホで開いても困らないように、スマホではできることとできないことを示してほしい

**受け入れ条件**:
- [ ] 画面幅が768px未満のときは、タイピング（モード1〜4）を開始できず、「PCで遊んでください」と表示する
- [ ] スマホでも、ストーリーの読み返し・用語辞典・DBの地図は見られる

**優先度**: P0(必須)

### 開発プロセスの要件（決定14・15）

このプロダクトは、問題とコードの両方が増え続けるため、作り方そのものを要件として決めておく。

- [ ] `/setup-project` で作った6つの永続ドキュメントに従い、機能ごとに `/add-feature` で作る
- [ ] **問題データの自動チェック**：全問の YAML が決まった形になっているか（Zod）、正解SQLが PGlite で実行できるか、モード2の選択肢が2つ以上あり正解が1つだけか、を確かめるテストがあり、1つでも失敗したらビルドを止める
- [ ] 判定ロジックの単体テスト（Vitest）、画面の動作テスト（Playwright：4モードそれぞれで1問を最後まで遊べる）がある
- [ ] **レビュー用の記録**：コードを作成・変更したら、`/add-feature` 1回ごとに `docs/review/YYYYMMDD-機能名.md` を作る。変更・作成・削除したファイルをすべて「変更したファイル一覧」に載せ、それぞれ何をしたかを書く。`git diff` のファイル一覧と照らし合わせて抜けがないことを確かめる。長さの上限はない
- [ ] `CLAUDE.md` に、上の2つ（問題データのチェック、`docs/review/` の記録）を「これを済ませるまで作業は完了しない」と書く

### 将来的な機能(Post-MVP)

#### 中級の章

`GROUP BY` / `HAVING` / 集計関数 / `INNER JOIN`・`LEFT JOIN` / サブクエリ / `CASE` / `INSERT`・`UPDATE`・`DELETE`。テーブルに `customers`・`orders` が加わる。

- 見える化A を中級の句に広げる：`GROUP BY` で同じグループの行が同じ色になって寄る、集計で1グループが1行に縮む、`JOIN` で2つの表の行が線でつながって1行に合体する、`LEFT JOIN` で相手のない行に `NULL` が入る
- 書き換え系の問題と、`WHERE` を付け忘れた `UPDATE` の事件
- 中級の内容＋初級の内容を組み合わせた複合問題。ターニングポイントは月次レポート

**優先度**: P1(重要)

#### 公開

Cloudflare Pages に静的サイトとして公開し、URLで開けるようにする。

**優先度**: P1(重要)

#### 上級の章

`WITH` / ウィンドウ関数 / 自己結合・3つ以上の結合 / インデックスと `EXPLAIN` / トランザクション / テーブル設計。上級＋中級・初級を組み合わせた複合問題。ターニングポイントはセール当日の障害対応。

見える化（作る順）：
1. インデックスあり・なしの左右比較（読んだ行数のカウンター、5万行ほどのデータで `EXPLAIN ANALYZE` の実測時間を並べる）
2. 実行計画の木の図（下から上へデータが流れ、行数が多いほど線が太い）
3. トランザクションの2列タイムライン（在庫1個に2人が同時に注文する場面。学習者が左右のSQLを実行する順番を選ぶ。PGlite は接続が1つなので、ここだけシミュレーション）

**優先度**: P2(できれば)

#### 実行前の予想クイズ（見える化D）

実行の前に「結果は何行になる？」「どの行が残る？」を当ててから再生する。

**優先度**: P2(できれば)

## 非機能要件

### パフォーマンス
- 初回表示：ページを開いてから章の一覧が操作できるまで 3秒以内（一般的な家庭用回線、2回目以降はキャッシュで1秒以内）
- PGlite の起動：章の一覧の表示を止めずに裏で起動し、最初の問題を開くまでに使える状態にする（起動中は「準備中」と表示）
- キー入力の反応：1回のキー入力から画面に反映されるまで 16ms 以内（打っている途中に引っかかりを感じない）
- 見える化C（打ちながら変化）：句を打ち終えてから表が変わるまで 300ms 以内（初級の 30行程度のデータで）
- 判定：実行ボタンを押してから結果が出るまで 500ms 以内（初級・中級のデータで）
- アニメーション：毎秒60コマで動く（一般的なノートPCの Chrome で）

### ユーザビリティ
- 初めて開いてから、1問目のタイピングを始めるまで、クリック3回以内
- タイピング中はマウスを使わずに最後まで進められる（会話送り・実行・次の問題まで、すべてキーボードで操作できる）
- すべての画面の説明文は日本語。SQL・テーブル・データの値は英語と数字だけ
- キーワードの説明（機能11）は、カーソルを当ててから 0.5秒以内に出る

### 信頼性
- 全問の正解SQLが PGlite で実行できることを、ビルドのたびに自動テストで確かめる
- 学習記録が壊れていてもアプリは起動する（機能12）
- 問題を始めるたびにDBを初期状態に戻し、前の問題の操作が次の問題に影響しない
- 書いたSQLが無限に終わらないとき（中級以降）、5秒で打ち切ってメッセージを出す

### セキュリティ・プライバシー
- 書いたSQLと学習記録は外部に送らない。SQLはブラウザの中の PGlite だけで実行する
- 個人情報を集めない（ログイン・アカウントなし）
- アクセス解析などの外部スクリプトを入れない

### スケーラビリティ（問題の増やしやすさ）
- 問題は YAML ファイルを1つ追加するだけで増やせる。コードの変更はいらない（新しい種類の見える化が必要な場合を除く）
- 最終的に 3章 × 約10問（＋複合問題）＝ 40問程度を想定し、問題数が増えても初回表示の速さが変わらない（問題データは章ごとに必要になってから読み込む）

### 対応環境
- ブラウザ：Chrome・Edge の最新版
- 画面：幅1280px以上を推奨。768px未満ではタイピングを開始できない（機能13）
- 言語：JavaScript（TypeScript は使わない、決定17）

## スコープ外

明示的にスコープ外とする項目:
- ログイン・アカウント・ランキング・他人との対戦
- サーバー（APIやDBサーバー）。すべてブラウザの中で完結する
- PostgreSQL 以外のSQL（MySQL・SQLite などの書き方の違い）
- 日本語入力（変換）を使うタイピング
- スマホ・タブレットでのタイピング
- AIによる添削・自由な質問への回答
- 英語など、日本語以外の画面表示
- 権限（`GRANT`）・ビュー・ストアドプロシージャ・`UNION`（必要になったら追加を検討する）
